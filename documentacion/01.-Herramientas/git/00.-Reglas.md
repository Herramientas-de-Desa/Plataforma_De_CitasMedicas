## Modelo de Ramas 

```
feature/* ──┐
            ↓
           dev
            ↓
         release/*
            ↓
           main
            ↑
          fix/*
```

## Reglas generales

| Rama | Propósito | Quién puede hacer merge |
| --- | --- | --- |
| `main` | Producción / código estable | Lead / Maintainer |
| `release/*` | Preparar una versión | Lead / Maintainer |
| `dev` | Integración del desarrollo | Developers |
| `feature/*` | Nueva funcionalidad | Cada developer |
| `fix/*` | Corrección de errores | Cada developer |

### 1. `main`

**Reglas:**

- ❌ Nadie hace `push` directo.
- ❌ No se desarrolla directamente aquí.
- ✅ Solo recibe cambios desde `release/*`.
- ✅ Requiere Pull Request.
- ✅ Requiere CI/CD exitoso.
- ✅ Requiere al menos **1 aprobación**.
- 🏷️ Cada merge debería generar una versión/tag.

```
release/1.2.0
       ↓ PR
      main
       ↓
    v1.2.0
```

`main` debe representar **exactamente lo que está en producción**.

---

### 2. `dev`

Es la rama donde se integra el trabajo diario.

**Reglas:**

- ❌ No hacer `push --force`.
- ❌ Evitar commits directamente sobre `dev`.
- ✅ Todo entra mediante Pull Request.
- ✅ CI debe pasar antes del merge.
- ✅ Las features deben estar revisadas.
- ✅ Mantener `dev` siempre compilable.

Flujo:

```
feature/order
      ↓ PR
     dev
```

---

### 3. `feature/*`

Cada funcionalidad debe tener su propia rama.

Convención:

```
feature/<nombre>
```

Ejemplos:

```
feature/create-order
feature/user-authentication
feature/payment
feature/product-search
```

**Reglas:**

- Se crea desde `dev`.
- Solo trabaja una funcionalidad por rama.
- No hacer features gigantes.
- No hacer `push --force` si otros trabajan sobre la rama.
- Antes del PR, actualizar con `dev`.
- El PR termina en `dev`.
- Una vez integrada, la rama se elimina.

```bash
git switch dev
git pull
git switch -c feature/create-order
```

---

### 4. `fix/*`

Para correcciones de errores que **todavía no están en producción**.

Ejemplos:

```
fix/order-validation
fix/null-user
fix/payment-calculation
```

Normalmente:

```
dev
 ↓
fix/bug
 ↓ PR
dev
```

**Importante:** si el error está **en producción**, no usaría `fix/*`; usaría `hotfix/*`.

Como tú has definido únicamente `fix`, entonces podéis establecer:

> `fix/*` sirve para cualquier corrección, incluyendo bugs de producción, pero el origen y destino dependerán del caso.
> 

Para un proyecto más serio, posteriormente añadiría `hotfix/*`.

---

### 5. `release/*`

Esta es la rama que usaría para **congelar una versión**.

Ejemplo:

```
release/1.3.0
```

Se crea desde:

```
dev
 ↓
release/1.3.0
```

Una vez creada:

```
release/1.3.0
       │
       ├── fix menores
       ├── documentación
       ├── configuración
       └── versionado
```

**No deberían entrar nuevas funcionalidades.**

Solo:

- 🐛 Correcciones.
- 📝 Documentación.
- 🔧 Configuración.
- 🧪 Ajustes necesarios para la release.
- 📦 Versionado.

Cuando está validada:

```
release/1.3.0
       │
       ├────────→ main
       │
       └────────→ dev
```

Esto último es **muy importante**: los cambios realizados durante la release deben regresar a `dev`.

---

# Flujo completo

```
                    feature/A
                   /
                  /
dev ─────────────┼───────────────
                  \
                   \ feature/B
                    \
                     ↓
                release/1.0.0
                   /       \
                  /         \
                 ↓           ↓
               main         dev
                 ↓
              v1.0.0
```

### Regla fundamental

```
feature/* → dev
fix/*     → dev
dev       → release/*
release/* → main
release/* → dev
```

Y **nunca**:

```
feature → main       ❌
dev → main           ❌
feature → release    ❌
```

# Reglas de Pull Request

Yo establecería estas reglas para **todas las ramas protegidas**:

### `dev`

```
PR obligatorio
    +
CI obligatorio
    +
1 reviewer
```

### `release/*`

```
PR obligatorio
    +
CI obligatorio
    +
1-2 reviewers
    +
QA / pruebas
```

### `main`

```
PR obligatorio
    +
CI obligatorio
    +
2 reviewers
    +
QA aprobado
    +
release aprobada
```

# Convención de commits

También os recomiendo establecer una convención desde el principio:

```
feat: agregar creación de pedidos
fix: corregir cálculo de impuestos
refactor: separar dominio de infraestructura
test: agregar tests de Order
docs: actualizar README
chore: actualizar dependencias
```

Por ejemplo:

```
feat(order): create order aggregate
fix(payment): validate payment amount
refactor(domain): extract money value object
```

Esto combina muy bien con un proyecto **DDD + Axon**, porque los commits empiezan a reflejar claramente qué está cambiando.

## La política que dejaría escrita para el equipo

> **`main` representa producción. `release/*` representa una versión candidata. `dev` representa la integración del desarrollo. `feature/*` representa nuevas funcionalidades y `fix/*` correcciones. Ninguna rama protegida recibe cambios mediante push directo; todo cambio entra mediante Pull Request, CI y revisión.**
> 

Con esas reglas ya tienes un **Git Flow ligero**, sin meter la complejidad de Git Flow clásico.
